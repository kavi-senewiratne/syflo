/btw — the throwaway side question

User request 2026-08-08: type /btw <question> in the chat composer, get an answer — but the exchange does not stay in the transcript. It is a quick aside ("by the way, what does logit mean again?") that must not pollute the thread, the branch context, or the mind map.

Four different answers to where the aside lives and when it disappears, plus the shared trigger UX and the open decisions. Everything is a mockup — nothing is built yet. Visual rule throughout: dashed borders + muted gray = temporary, solid + blue = permanent.

00 Shared trigger — the slash menu and the mode chip

Identical in all four variants. Typing / as the first character of an empty composer opens a small command menu; anywhere else / is just a slash (URLs, dates, math). Picking /btw turns the prefix into a chip — so the user always sees which mode they are sending in, and can leave it with Backspace or the ×.

  • Typing shortcut: /btw plus space converts to the chip immediately — no menu needed once the user knows the command. Keyboard alternative: Alt+B toggles the chip.
  • Leaving the mode: Backspace on an empty composer removes the chip (like removing a file attachment), as does the ×. Esc clears chip and text together.
  • The eye-off line under the composer is the promise: it names the consequence before sending, not after. It replaces the model chip row only while btw mode is on.
  • Not a new file-type of message: the aside uses the same model and the same provider ladder as a normal message — only its persistence differs.
01 Idea A — ghost bubbles in the transcript

The aside appears where the user is already looking: at the bottom of the thread, but drawn as dashed "ghost" bubbles behind a vertical dashed rail. It reads like the normal conversation, just clearly marked as not-really-there. It vanishes on the next real message (or on Dismiss), and Keep converts it into two ordinary, permanent bubbles.

  • Strength: zero new surfaces. Reading flow, markdown, KaTeX, code blocks, copy buttons, question-nav — everything the normal bubble does, the ghost bubble does, because it is the normal bubble with a modifier class.
  • Weakness: the aside still scrolls the thread and pushes real messages up. If the user asks three asides in a row, the transcript looks messy until they clear.
  • Undo window: the toast keeps the discarded pair recoverable for ~10 s; after that it is gone from memory and never written to the database.
  • Multiple asides: only the newest ghost block survives — asking a second /btw replaces the first (with the same toast), so the thread can never accumulate ghosts.

  • Strength: the promise is visibly kept — the transcript literally never changes, so there is nothing to un-write and no scroll jump.
  • Weakness: the card covers the last one or two messages, exactly the ones the aside is usually about. Mitigation: the card is draggable by its header, or collapses to a one-line strip on hover-away.
  • Follow-ups: asking a second /btw while the card is open appends a Q/A pair inside the card (it scrolls internally) — so a short side conversation is possible without ever entering the thread.
  • "Make a branch" turns the aside into a real branch chat whose parent quote is the aside's question — the one path where an aside becomes permanent without touching the current thread.
03 Idea C — a side lane next to the chat

The asides get their own narrow column, like the Highlights drawer: a scratch lane that slides in from the right the first time /btw is used. It holds several asides at once as a short stack, survives while the user keeps reading — and is emptied when the chat is left. The transcript stays untouched, and nothing covers it.

04 Idea D — the composer answers itself

The most minimal option: the composer grows a fold-out panel upward and the answer appears inside it, as part of the input area rather than as a message. Nothing floats, nothing scrolls, nothing is added to the thread. The next keystroke in the composer collapses it.

Side question
how does layer normalisation differ from batch normalisation?
Batch norm normalises each feature across the examples in a batch, so its statistics depend on batch size and composition. Layer norm normalises across the features of a single example, so it is independent of the batch — which is why sequence models use it: sequences in a batch have different lengths, and inference often runs with a batch of one. In the Transformer, layer norm sits around every sub-layer together with the residual connection.

  • Strength: smallest change of all four — one panel above the input, no overlay, no drawer, no message-list branching. The dismissal rule ("start typing") needs no button at all.

D is the cheapest to build and a reasonable fallback if the overlay proves annoying.
06 Decisions the mockups do not settle

These change the backend, not the pixels — worth agreeing on before any variant is built.

  1. Does the aside see the chat? The interesting case is asymmetric: the aside reads the thread (so "what does this mean?" works without repeating context), but the thread never sees the aside. Alternative: a fully isolated aside with no context at all — cheaper, faster, but then "logit" has no paper around it.
  2. Does the aside survive a reload? In-memory only means an accidental refresh loses it — matching "throwaway" honestly. Or persist with an ephemeral flag so the answer survives a crash and is filtered out of the transcript, the branch context and the mind map. The flag is more code, and every query that reads messages has to remember it.
  3. Do asides count toward quota and cost? They are real model calls, so yes — but should they use the same model as the chat, or always the cheap/fast rung of the ladder? A dedicated "side-question model" in settings would keep asides free while the thread runs on a paid model.
  4. What does "Keep" actually write? Append the pair at the current end of the thread (simplest), or insert it at the position where it was asked (truer to the reading order, but rewrites message order). Also: does a kept aside then become part of the branch context like every other message? Presumably yes — once kept, it is an ordinary message.
  5. Highlights and quoting. Can text in an aside be selected to create a branch or a highlight? If highlights point at a message id that never exists, the answer has to be "no" — or "Keep" is triggered implicitly the moment the user highlights inside an aside.
  6. Naming in the UI. The command stays /btw, but the label the user reads: "Side question" / "Nebenfrage", or "Aside", or "Scratch". Both language halves of strings.ts need the pair before anything is built.
