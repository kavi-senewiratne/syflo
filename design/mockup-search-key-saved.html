Search-key saved — what the old card shows afterwards

Today, clicking Save & retry on the search-wish card stores the key and re-sends the question — and the card itself does not move. keyFieldOpen stays true, the input keeps its dots, the button returns from Saving… to Save & retry: the bubble looks exactly as if the click had been swallowed (user report with screenshot, 2026-09-12, Matrix theme).

Source today: MessageBubble.tsx → SearchWishCard, placement D from mockup-search-wish-placement.html. Every colour below is a standard token, so all five themes hold.

What the running app showed on 2026-09-12

  1. The key was stored correctly — settings.tavily_api_key holds it, and the re-asked question went out.
  2. The tool was offered — the new answer carries no search_wish error, so web_search was on the table.
  3. But the model never called it. The identical question plus its own refusal sit one turn above in the history, and it paraphrased itself (“nach wie vor”). Known trap from 2026-08-25: models skip the tool unless pushed.
  4. So this mockup has a backend twin: the re-ask after a key save must carry a search nudge (an instruction naming the wished-for query, or a forced tool choice where the provider supports one). Without it, every variant below confirms a search that never ran.

Two failures share this screen. The card failing to acknowledge the save is the visible one; the second answer repeating the first is the backend one (diagnosis above). The variants below fix the first and make the second impossible to miss.

§02 Variant A — the receipt: two steps while it runs, one check when it’s done

Chosen 2026-09-12, iterated five times the same day. The passes, each ended by a user report: (1) one cramped 11.5 px line; (2) fact and consequence split, but the spinner sat next to “Search key saved” and read as “the search is running”; (3) two steps with two checkmarks — noise; (4) two steps only while something runs, settled as one line — chosen over the arrow treatment; (5) that one line still carried the teaching clause in the same breath.

Fifth pass: “web search stays on for every future answer” is an aside, not part of the receipt — it moves to its own faint line. Which face ships is decided by the rest of the app (user rule 2026-09-12): the trade below cites the existing precedents.

Gains

Exactly one checkmark in every state, and the receipt line stays short enough not to wrap. The aside can be dropped later (once every user knows searches persist) without touching the receipt.

Costs

The receipt confirms the gesture, not the outcome — honest about the asking, silent about whether a search ran (§01’s second failure). No path to the new answer in a long chat.

With the info mark

Matches the app’s existing hint vocabulary: the model picker’s local-hint row and the settings hints already set Info at 13 px in gray-400 beside gray hint text (ModelPicker.tsx local-hint-row, SettingsModal key hints). The mark declares the register switch — a note, not a step. Cost: an info icon can promise a tooltip it does not have — the app’s precedents are clickable rows or sit in settings prose.

Bare indented line

Precedent is thinner: the ask-card’s allowance aside (“free, ~33 a day”) is faint plain text without an icon — but it sits beside a button in a foot row, not indented under a checklist. Quietest option, no new glyph; the indent under a check can read as step 2’s continuation rather than as a footnote.
§03 Variant B — status that follows the retry

The card becomes a live status of the re-ask and reports the outcome, not the gesture: whether the new answer actually searched. The frontend already knows — a search puts sources on the new message; their absence is the honest third state, with the one action that repairs it.

Gains

The only variant that would have caught 2026-09-12: “answered without searching” names the failure instead of hiding it behind a confirmation. The jump link gives the save a destination in a long chat.

Costs

Three states to build and test, and the third needs the backend twin (a re-ask that forces the search) to have anything to offer. The old bubble keeps doing work after its moment has passed.

§04 Variant C — the card retires, the new answer carries the news

The old bubble keeps only a faint one-line remnant; the confirmation moves to where the reader is already looking — the new answer, which shows its sources strip plus a one-time “first search” chip naming the query that ran.

Gains

The proof sits next to the evidence: sources under the answer they produced. The old bubble goes quiet forever — no furniture accumulating in the scrollback. The chip teaches what changed (“web search is on”) exactly once.

Costs

Everything hangs on the search actually running — if the model skips the tool, the chip and the strip never appear and the save is silent again (§01, second failure). Needs the streaming pipeline to mark “first search after key save”, a flag that crosses two messages.

§05 After a reload

The save-and-retry moment is transient — searchWish persists in the DB (search_wish_query/search_wish_error), the click does not. On reload, every variant falls back to the stored-key face the component already has: the caveat without an action. The differences are what else survives.

A · receipt

Gone after reload; the caveat line returns. Consistent with the receipt being about the gesture.

B · status

State 2/3 could persist if the outcome is derivable (the next assistant message’s sources), so the honest failure stays visible across sessions — the strongest argument for B, and the most persistence work.

C · remnant + chip

The remnant needs a persisted “key saved at this message” marker to survive; the sources strip persists already, the chip does not have to.
