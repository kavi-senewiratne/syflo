Sidebar — user categories with one nested level, everything collapsible

The root list has exactly two organising principles today: the Pinned section at the top and the relative date sections below it (“Today”, “Yesterday”, “This week”, …). Both are assigned by the system — the user cannot say these five trees belong together.

This mockup adds a third principle the user owns: categories (named folders), each of which may contain subcategories one level deep, and it makes every section — Pinned, categories, subcategories and the date sections — collapsible, with the open/closed state remembered across restarts.

The frame. A category is a container for root chats (trees), never for branches — the same scope as pinning. Depth is capped at two: category → subcategory → chats; a subcategory holds no further subcategory. A chat sits in at most one category, so nothing is listed twice. A categorised chat leaves the date sections exactly as a pinned chat does today. Colors stay in the standard token families (gray-* for structure, blue-* for active and drop states), so all five themes remap them.

§01 · What a category row looks like

Three shapes for the same data. The question underneath is whether a category reads as a heading (like the date sections it replaces) or as a row (like the chats it holds) — that decision also fixes how much a category can carry: a heading has no room for a menu button, a row does.

The category is announced the way “Today” is: 11 px uppercase, gray-400, with a chevron in front. Categories and date sections form one visual ladder. Nothing on the row but the name; renaming and deleting live in the right-click menu.

§06 · What the pieces cost, side by side

Space

  • Sidebar width is w-64 = 256 px, rows px-2.5. A chat at depth 2 starts 38 px in, leaving ~200 px for the title before the PDF/YT tag.
  • Every extra chevron column pushes the whole list 16 px right, including the date sections that need none.
  • Counts on closed sections are the only thing that distinguishes “closed” from “empty”.

Interactions that already exist

  • Pin/unpin, rename, delete are right-click only, with no control on the row (user decision 2026-08-11) — a “…” button on category rows breaks that rule for one row type.
  • Keyboard navigation (ADR-0011) walks data-focus-item. Collapsing must remove hidden rows from that walk, and ← / → are the natural close/open keys — they are currently region switches.
  • The tree view (branches) has its own chevrons; a category chevron at the same size in the same column may read as “this chat has branches”.

Data

  • Categories need their own table (id, name, parent_id, position) and one nullable category_id on the chat — a subcategory is just a category with a parent.
  • The two-level cap is a rule to enforce on creation, not something the schema prevents.
  • Open/closed state and manual ordering are user state, not chat state — they belong next to the sidebar’s collapsed flag, not in the chats table.
Open questions this mockup does not answer.
  • Pinned versus categorised. A chat that is both pinned and filed — does it appear in Pinned, in its category, or in both? §04-A implies Pinned wins; §04-B implies both.
  • Ordering inside a category. Newest first like everywhere else, alphabetical, or a manual order the user drags? Manual order is the reason to have a category at all for some users and dead weight for others.
  • Branches. Categories hold trees. A branch cannot be filed separately — worth confirming, since /branch can create a tree that feels like its own topic.
  • Mindmap view. The sidebar has a chat/mindmap switch. Do categories appear there, or is the mindmap unaffected?
  • Auto-filing. Nothing here suggests the model proposes a category. Deliberate — but it is the obvious next question once the containers exist.
