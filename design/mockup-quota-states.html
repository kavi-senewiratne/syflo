Quota exhaustion — every state of the token-limit journey

What the chat shows as cloud tokens run out, in the order the user experiences it: short waits (01), silent failover between models (02), and the end of the ladder when every candidate is cooling down (03–05). Sections 04–05 replace the current all-exhausted card: Retry disappears while it cannot work, a reset-time line says when the cloud comes back, and the local model becomes the primary way out. Section 06 surfaces the same information proactively in the model picker. Sections 04/05/08 carry the copy v2 proposal (2026-07-26): one precise message per cause (quotaReason: daily / minute limits / request too large) instead of the generic “alle Cloud-Kontingente sind aufgebraucht”. German copy comes from strings.ts (DE); backend behavior from routes/messages.js (ADR-0008, slice 5). See also: mockup-model-flow.html (2026-07-26) — the audited companion covering the FULL journey around these cards: verified per-state status map, grouped picker, the swallowed-error cards, queue transparency, the Interrupted exit and the local→cloud privacy guard. All of it was BUILT the same day (2026-07-26): the picker is now grouped with unfiltered cross-provider badges, and the deviations listed there (daily-card clock, billing-link provider, retry re-arming) are fixed.

04 Daily limit — no retry, reset time shown built · copy v2 proposed 2026-07-26

When the earliest cooldown expiry (retryAt, sent with the SSE error) lies far ahead — the daily-limit case — the retry button is gone. A quiet clock line answers the open question (“when can I use the cloud again?”), the local model becomes the single, visually primary way out. “Voraussichtlich” and “ca.” stay in the copy: UTC midnight is an estimate and cooldowns live in memory. Copy v2: the message names the CAUSE (“Tageskontingent”) instead of the generic “alle Cloud-Kontingente … aufgebraucht” — the backend sends a quotaReason ('daily' | 'rate_limit' | 'too_large') alongside retryAt, live incident 2026-07-26: 18/250 daily used, yet the card suggested everything was gone. Decision (user, 2026-07-26): NO “Modell wechseln” button here — with a daily limit the failover has already tried every keyed cloud model, switching cannot help. Structure v3 (user feedback: too much text): one line per purpose — message, clock line, button row, footnote. The upgrade instruction becomes the “Limit erhöhen” button (external-link icon): it opens the provider's billing page in the browser (URL per provider from registry.json), and its tooltip carries the explanation “Bezahlter Plan bei deinem Anbieter — dein API-Key in Syflo bleibt derselbe.” BYO-Key (ADR-0008): no app change needed.

05 Short cooldown (90 s) — retry comes back on its own built · copy v2 proposed 2026-07-26

After three failed attempts against per-minute limits the cooldown is only 90 s — here a retry does work, just not yet. Chosen treatment: the button stays visible but disabled, with the countdown inside it — the affordance stays discoverable. (A hidden-button variant with a countdown info line was considered and dropped.) Copy v2: “an ihren Minuten-Limits” names the real cause — “aufgebraucht” read like the daily quota was gone (live confusion 2026-07-26: 18/250 used). A quiet second line explains WHY the minute budget empties faster than expected: question bursts and web-search rounds each count as extra requests.

07 After a reload — generic failed row exists · unchanged

The quotaExhausted flag is transient by design: the persisted *Failed* marker loses it on reload, and the in-memory cooldowns are gone after a backend restart anyway. So a reloaded failed message shows the plain row with a plain retry — which is honest again, because nobody knows the cooldown state anymore.

08 Request too large — no retry, no countdown proposed 2026-07-26

The third cause the generic card hid: the question plus its context (a 15k-token paper chat) exceeds a provider's per-request/per-minute token budget (Groq: ~8k TPM). Waiting does NOT help — the same request fails deterministically — so the card shows neither a retry button nor a countdown. Structure v3 (user feedback: too much text): message line + three buttons + footnote, nothing else — the explanations live in the buttons' tooltips. Local stays primary; “Modell wechseln” opens the picker (bigger-budget model often fits; §06 badges show which); “Limit erhöhen” opens the provider's billing page (paid plans lift token budgets too). Backend: the existing too_large branch sends quotaReason: 'too_large'; the frontend picks this copy and suppresses retry regardless of retryAt.

Why no retry: unlike 04/05 this failure is size-dependent, not time-dependent — a retry sends the identical oversized request. Showing a countdown here would promise a fix that never comes. Exception (user request 2026-07-26): once the user actually SWITCHES the model (via the picker), an enabled „Erneut versuchen“ appears on the card — the newly picked model may have the budget the failed one lacked. Applies to the daily card too (e.g. after switching to the local model). Auto-retry (user decision 2026-07-29): when the picker was opened FROM this card („Modell wechseln“), picking a DIFFERENT model retries this answer immediately — no second click. Dismissing the menu without a pick disarms the auto-retry; the enabled-retry exception above stays as the fallback for switches made anywhere else (pill, Settings).

Copy v3 summary (all three causes, final 2026-07-26): every card is message line(s) + button row + footnote; explanations live in tooltips. daily → message + clock line + [Lokal (primary)] [Limit erhöhen ↗]; minute → message + burst explainer + [Erneut versuchen (countdown)] [Lokal (primary)]; too large → message + [Lokal (primary)] [Modell wechseln] [Limit erhöhen ↗]. “Limit erhöhen” opens the provider's billing page — URL per provider in registry.json. EN strings mirror DE 1:1 in strings.ts.
