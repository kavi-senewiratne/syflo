Branch trace — what /btw and /branch leave behind in the parent chat

A branch opened from a selection already leaves a trace: the passage stays coloured in the parent chat and carries message_highlights.child_chat_id, so the parent shows where the branch grew out of and one click jumps into it.

/btw and /branch have no passage. Today they leave the parent chat completely untouched — the new branch exists only in the sidebar and in the mindmap. Reading the parent later, there is no sign that the conversation forked here, and no way back into the branch from the transcript.

What these two commands do have is a place in time: the last message that existed when the command was sent. That is the anchor every variant below uses — the branch is drawn at the point in the transcript where it was opened.

Decided and built — 2026-08-09

  • Variant A — a branch line in the transcript. Variants B and C stay here as the record of what was weighed.
  • Selection branches keep only their coloured passage (option 1) — the line belongs to the branches that have no passage.
  • The way back is part of it (§07, user requirement): from inside the branch, one click returns to its line and makes it glow.

06 Recommendation and what it costs to build

Recommendation: variant A, only for /btw and /branch

A is the only variant whose anchor is a moment rather than a message, and the fork order is exactly what is missing today — the sidebar already answers “which branches exist”, the transcript should answer “when did I go off here, and what did I ask”. It is visible without hovering, it survives on touch, and it needs no horizontal space. C is the runner-up and is cheaper; B is too quiet for something the user is meant to notice while re-reading.

The data that is missing

  • One migration on chats: branch_anchor_message_id TEXT REFERENCES messages(id) ON DELETE SET NULL — the last message in the parent when the branch was created. parent_id already says which chat, this says where in it.
  • A second column branch_origin TEXT ('btw' | 'topic' | 'selection') so the line can label itself. Selection branches can be recognised through message_highlights.child_chat_id too, but an explicit column keeps the render path from doing a join per line.
  • Written in exactly two places: routes/btw.js (/keep) and the POST /chats call behind handleOpenTopicBranch. For /branch with a target picked in the chip, the anchor is the last message of the chosen target, not of the chat the user is looking at.
  • Existing branches get NULL and simply show no line. No backfill by guessing timestamps.

Traps this touches

  • Message order is not id order. Since messages carry UUIDs, “the last message” must come from rowid / created_at, not ORDER BY id — the same trap the /btw work already hit.
  • The started SSE event rebuilds the user message by hand. Any branch line rendered from message data must also be fed there, or it vanishes until the next reload.
  • The question stepper and its scroll spy walk the message list; a new row type in the stream must be skipped there, not counted as a question.
  • cleanupAbandonedChat deletes empty root chats on navigation. A trace pointing at a chat that is about to be swept must not resurrect it — the line reads the branch list, so a deleted chat drops out on its own.
Naming: “Branch trace” for the glossary in CONTEXT.md — the mark a branch leaves in the chat it was opened from. The coloured passage of a selection branch is the trace Syflo already has; this extends the idea to branches with no passage.

Decided and built (2026-08-09)

  1. Variant A, for /btw and /branch only — selection branches keep their coloured passage as the single trace (option 1).
  2. The pill carries the raw command, /btw and /branch, untranslated — same rule as the panel's name and the slash menu.
  3. A click switches to the branch, exactly like clicking a highlight today.
  4. The stack folds after two lines ("1 weiteren Branch anzeigen"), and unfolds itself when a jump targets a hidden line.
  5. The way back is §07: the quote link for /btw, a new second header line for /branch. Both switch to the parent and glow the line — the parent-context pane shows messages only, so it cannot host a branch line.
