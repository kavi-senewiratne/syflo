Keyboard navigation — one focus ring, no mode

Decided 2026-08-10 · ADR-0011 · glossary: keyboard region, focus ring, edge overflow

Every region of Syflo reachable from the keyboard, using arrow keys only — and adding exactly one new visual element to the app: the focus ring. No mode indicator, no status bar, no new panel, no new button.

The trick that makes a mode unnecessary: a text field and a list item are different focus targets. The browser already knows which one holds focus, so ← can move the caret in the composer and jump between regions on a chat row — same key, no hidden state to remember.

01 The focus map
The map is an L, not a row: four regions left to right, plus the mind map lying across the top (App.tsx:2270). So ← → alone cannot reach everything — ↑ from the topmost item of a column overflows into the map, and ↓ from the map drops back into the column below it (decision 2026-08-10). Each region is a single stop: entering it lands on the item you last used there, not on its first item.
A region that isn't on screen — mind map while the chat is showing, highlights drawer while it's closed — is skipped. A region that is on screen is never skipped, even when it has nothing in it yet: a paper with no highlights falls back to focusing the page, so ↑ ↓ turn pages. The map must stay memorable, and a region that appears the moment you make your first highlight would make it un-memorable (decision 2026-08-10).

Everything interactive is an item (revised 2026-08-11) — not only the obvious lists. The composer's own buttons and the collapsed sidebar's rail count too; without them the arrows walked past whole controls, and a folded sidebar dropped out of the map so ← out of the PDF hit a wall. A control the layout has hidden is not an item: the model picker is display:none in a narrow chat column, and a ring on it simply vanished.
The source region and the drawer both list highlights — deliberately, and they are not the same list. The source holds the highlights of the page you are looking at, in reading order; the drawer holds every highlight of the whole tree, grouped by colour. Same objects, two different questions: "what is marked here?" versus "what have I marked at all?"

What to feel for: in the composer, ← moves the caret like it always has. One esc later, the very same key leaves for the source pane. The ring is the only thing that changed, and it is always visible.
03 Why the ring cannot be blue
Colour is already spoken for in three places. Blue means "this chat is open" (the sidebar's bg-blue-50 / text-blue-700 pill), blue is also one of the five highlight kinds (#2563EB — the drawer's left bar and the map node's colour bar), and the map fades filtered nodes. A blue focus ring would land on top of all three and say nothing new.
The ring therefore carries no hue of its own: a halo in the surface colour, then a line in the text colour. Those two contrast with each other by definition, in every theme, on every ground — including a highlight card that happens to be blue.

The blue pill still means "open", the colour bar still means "highlight kind". The ring adds a third, separate channel and never competes with either.
Three signals, three channels: fill = which chat is open · left bar = highlight kind · outline = where the keyboard is. All three can be true of the same row at once, and all three stay legible. The ring uses --surface and --text-strong only — no blue-*, no hardcoded colour, so every theme carries it for free.
04 The chevron conflict — the edge-overflow rule
The chat tree already collapses with a chevron (ChatTree.tsx), and the standard tree pattern gives ← / → to collapse / expand. That collides with using them to change region. The rule that resolves it: arrow keys serve the tree first, and only leave the region once the tree has nothing left to do. The same rule carries the vertical axis (§01): ↑ moves between items, and only once there is no item above does it overflow into the mind map. One rule, both axes, nothing extra to learn.

05 Escape keeps its old job — it just gains a last step
Escape closes the topmost open thing today, in twelve places. It keeps doing exactly that. The new behaviour sits at the end of that chain: when there is nothing left to close, Escape hands focus to the structure. A user who never learns this loses nothing.

The ring appears on whatever the app already marks as current — the open chat's row in the sidebar. Afterwards it returns to wherever it was left (revised 2026-08-11).
And back: any printable key returns focus to the composer and types that character — the same silent rule /btw already uses for dismissal. So there is no "how do I get out of here" moment, which is precisely what a mode would create.
06 The whole keymap
Nine bindings, all of them arrows or keys the user already presses. Nothing to memorise in order to get started — the first esc is enough, everything after it is discoverable by pressing arrows and watching the ring.

New UI elements: one — and one only. The focus ring on the item: box-shadow: 0 0 0 2px var(--surface), 0 0 0 4px var(--text-strong). No region outline, no mode badge, no status bar (decision 2026-08-10). It borrows no hue from anything that already means something (§03) and uses only surface/text tokens, so all five themes carry it for free.
What the keyboard still cannot do, stated plainly: select part of a bubble. ↵ takes the bubble whole, so you can branch off an entire answer but not off the one sentence inside it — that stays a mouse gesture. Character-level selection with shift+arrows was considered and dropped: it would hand ← → back to the caret inside a bubble, which is exactly the ambiguity this whole design exists to avoid.
