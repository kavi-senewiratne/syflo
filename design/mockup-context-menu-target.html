Sidebar — keep the right-clicked row marked while its context menu is open

Today the row you right-click loses every visual trace the moment the menu appears: its only marking is hover:bg-gray-100, and the invisible full-screen backdrop (z-40, Sidebar/index.tsx) takes the pointer away from the row, so the hover state ends instantly. With the menu floating at the cursor over a tree of similar rows, “Rename / Delete” no longer says what it will rename or delete.

All variants below show the same tree and the same open menu, so the treatments are directly comparable. Each is shown twice: on an inactive row, and on the active (blue) row — the marking has to survive both.

The rule. While a context menu is open, exactly one row is its target, and that row must look different from every other row — including from a row that merely happens to be hovered and from the active chat. Colors stay inside the standard token families (gray-* for the neutral marking, blue-* when the target is also the active chat), so all five themes remap them.

Variant A — hold the pill

A1 inactive row
The gray-100 pill the row had under the cursor simply stays until the menu closes. Nothing new is invented — the marking that exists today just stops vanishing.

Notes on the implementation, whichever variant wins.
  • The marking is driven by the existing contextMenu.chatId state in Sidebar/index.tsx — it is passed down to ChatTree (and used directly in the flat “All chats” list) as contextMenuId, next to activeChatId and renamingId.
  • It disappears exactly when the menu does: outside click, Esc, or picking Rename/Delete (Rename then marks the row its own way, with the inline input).
  • Both places that open the menu get it: the tree rows in ChatTree.tsx and the flat root rows in the default “grouped by date” view.
  • No new colors: gray-100/300 and blue-100/400 are remapped by every :root[data-theme] block, so the marking follows all five themes.
