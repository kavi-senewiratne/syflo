/btw — Idea D, the composer fold-out

Round 3, 2026-08-08. The answer to a /btw side question appears above the input field, as part of the composer — never as a message. The transcript is never written to.

Settled so far

  • The panel is called /btw, not "Side question" — it names the command that made it, so the label needs no translation and teaches the trigger every time it opens.
  • The first keystroke makes it disappear — gone, not folded into a leftover line.
  • The × stays, and clicking it does the same thing. Neither it nor Esc is ever explained in the UI.
  • An exhausted model switches itself — the aside walks down the ladder without asking and mentions in one gray line who answered.
  • Long answers scroll inside the panel, capped at 40 % of the pane — with a grip to drag it to 75 %, and a swap of the two buttons once an answer stops being an aside. Section 04.
  • "Make a branch" opens the branch from section 03 — and the answer is the first bubble; the question lives in the "Branched from" header, not as a message.

02 Every way out

Everything in the "silent" column happens without a word of UI copy. There is no confirmation anywhere — discarding an aside is the promise of the feature, not a loss.

Gesture Silent? What happens
Type in the composer Yes The panel is removed on the first character that changes the text. The aside is discarded — not recoverable.
Esc Yes Same, immediately. While streaming it stops the stream first, then removes the panel.
× in the header Visible, unlabelled Same. The only exit a mouse-only user can see.
Send a normal message Yes Already gone by then — the first keystroke did it.
Ask a second /btw Yes The new answer replaces the old one in the same panel. Only ever one aside at a time.
Open another chat or branch Yes Kept — the panel belongs to its chat and is waiting when you come back. See section 05.
Mind map, home, settings Yes Kept — the chat was never left, only covered.
Reload / restart the app Yes Gone. Asides live in memory only and are never written to the database.
Click anywhere else — Nothing. Scrolling, selecting text, opening Highlights all leave the panel alone — it is part of the composer, not a popover.
Keep in chat — Panel closes, two real messages appear at the end of the thread.
Make a branch — Panel closes, a new branch opens with the answer as its first bubble.
03 What the two buttons do

Keep in chat appends the pair at the end of the thread as two ordinary messages — from then on they are normal in every way (branchable, highlightable, part of the context a child chat inherits). Make a branch opens a branch chat whose parent quote is the question — so the question lives in the header, and the answer is the first bubble. The current thread is left untouched either way.

  • No duplicate question in the branch. The header already carries it as the branch quote — repeating it as a user bubble would say the same thing twice, and every other branch in Syflo starts the same way: quote above, answer below.
  • The branch's parent is the chat the aside was asked in, so it hangs under that chat in the mind map exactly like a branch made from a highlight.

how does layer normalisation differ from batch normalisation?
Batch norm normalises each feature across the examples in a batch, so its statistics depend on batch size and composition. Layer norm normalises across the features of a single example, so it is independent of the batch — which is why sequence models use it: sequences in a batch have different lengths, and inference often runs with a batch of one. In the Transformer, layer norm sits around every sub-layer together with the residual connection.

walk me through the whole encoder-decoder architecture
The encoder is a stack of six identical layers. Each layer has two sub-layers: multi-head self-attention and a position-wise feed-forward network, each wrapped in a residual connection followed by layer normalisation. The decoder adds a third sub-layer that attends over the encoder's output, and its self-attention is masked so a position can only attend to earlier positions. Positional encodings are added to the input embeddings because the architecture itself contains no notion of order…

  • 1 · The floor. The panel never grows past 40 % of the pane; the answer scrolls inside while question, header and buttons stay put. The fade at the bottom edge is the whole "there is more" signal — a scrollbar alone is easy to miss in a 90 px box.
  • 2 · The grip. A 24 px bar at the top edge, draggable up to 75 % of the pane. No button, no label, no state to remember: let go and the height stays for this aside only; the next one opens at 40 % again. This is the one place where a long answer is genuinely the user's problem to solve, and dragging is the gesture they already expect from a panel edge.
  • 3 · The admission. Past a threshold — I would take roughly 900 characters, or any answer containing a code block or a table — the two buttons swap places, so Make a branch comes first. Nothing is said, nothing is forced: the panel just makes the right exit the obvious one. An answer that long is not an aside any more, it is a conversation that deserves its own chat.
  • What I did not choose: a "Show more" button (adds a third click and a second expanded state to reason about), letting the panel push the transcript off-screen (breaks the promise that the thread stays readable), and auto-branching without asking (a branch appears in the sidebar and the mind map — too permanent to happen by itself).
  • While streaming a long answer the panel grows to the 40 % cap and then auto-scrolls with the text, exactly like the message list does. Once it is done, it stays scrolled at the top — the beginning is what the user asked for.

  • The switch is automatic and silent while it happens — no "trying another model…" step, no dialog. The user sees a spinner, then an answer. The gray line appears only when the responder was not the chat's own model; in the normal case there is no model line at all.
  • The chat's own model is not changed. The next real message goes to Gemini Flash again (or to whatever the quota rules say) — the aside borrows a model, it does not reconfigure anything.
  • An aside is never queued. If the local queue is busy, the aside takes a cloud rung instead of waiting in line — a side question that arrives two minutes later has missed its moment.
  • If every rung is exhausted, the panel says so in the same one-line gray voice ("No model available right now") and keeps its × — still no Failed entry in the transcript, because an aside has no message to fail.
06 Navigating away — the panel belongs to its chat

Your question: what if another branch is opened, or the mind map, or home? The aside is scoped to its chat, not to the screen. Leaving for another chat leaves the panel behind, untouched; coming back finds it exactly where it was. Nothing is marked, nothing is announced — the composer simply still has it. Only a reload clears everything, because asides never reach the database.

  • Why keep it instead of discarding on every switch? Reading a paper means jumping constantly — into the mind map, into a branch, back. If the aside died on each jump it would die exactly when the user goes to check the thing the aside was about. Discarding is what typing and Esc are for, and both are one gesture away.
  • One aside per chat, at most. Two chats can each hold one; a third /btw in the same chat replaces that chat's aside. No list, no counter, nothing to manage.
  • The sidebar dot in beat 2 is optional — a 5 px gray dot on a chat that has an aside waiting. It is the one place a marker would help; it may also be too much bookkeeping for a throwaway feature. Say which you want.
  • Streaming plus navigation: if the user leaves mid-stream, the answer keeps streaming into the panel in the background and is complete when they return. It is one request, already in flight — cancelling it would waste the tokens it already spent.
  • Every aside dies on reload, in every chat, with no trace anywhere — that is what "not saved" is for.
07 Still open

Everything else is decided. These four change code.

  1. The sidebar dot Mark a chat that has an aside waiting, or leave the sidebar completely alone? A dot makes the "it is still there" rule discoverable; no dot keeps the feature invisible, which is its whole point.
  2. Does the aside read the thread? Asymmetric is the useful default: the aside sees the conversation (so "what does logit mean" lands in context), the conversation never sees the aside. Full isolation is cheaper but makes short questions useless.
  3. The long-answer threshold Section 04's third state swaps the buttons past roughly 900 characters, or any code block or table. That number is a guess and should be checked against real answers before it is written down — too low and every second aside pushes toward a branch, too high and the swap never fires.
  4. German wording The panel header is now /btw in both languages, so only the buttons need their DE half — "Im Chat behalten" and "Verzweigen" — plus one line for the automatic model switch.
