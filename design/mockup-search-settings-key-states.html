Web-search settings — the stored key deserves a different page

The Web search tab (W3) shows nearly the same furniture whether a key is stored or not (user report with screenshot, 2026-09-12, Matrix theme). Source today: SettingsModal/index.tsx, tab search.

Standardization rule (user, 2026-09-12): this tab must match the Model tab’s key step — one design language for every key in the app. So the EMPTY state is the same in all variants below: input plus the Model tab’s guide block carrying the whole sell (allowance, link, without-a-key note), rendered only while nothing is stored. The variants differ only in what the STORED state shows.

What confuses today's stored state

  1. The key is invisible. The user saved a key from the chat card, opens this tab — and sees an empty input. Only the small badge says anything was stored; the page's largest element says the opposite.
  2. The sell outlives its sale. “1000 searches a month free, no credit card”, “Get a free key”, and “without a key Syflo answers only from the model’s knowledge” are all arguments for getting a key — argued at someone who already has one.
  3. The precedent is one tab away. The Model tab already does this right: its key guide (data-testid="key-guide") renders only while !keySetFor(provider), the “Key saved” mini-badge sits on the step label, and Remove sits beside the input. The search tab predates that pattern.

Reproduced from the component. The only differences between the two states: the badge text, the input placeholder, and a “Remove key” link. Every selling line stays.

§02 Variant A — two faces, masked chip

The stored state collapses to the three things that are still true: the key exists (a masked chip where the input was), it can be replaced, it can be removed. The empty state is the standardized Model-tab form — input plus guide block; “Replace” opens that input back up.

Gains

No backend change — the chip is generic dots plus the fixed tvly- prefix. The page halves; every remaining element has a job, and the empty state is byte-for-byte the Model tab’s pattern.

Costs

Generic dots prove that a key is stored, not that it is the reader’s key — the “is mine really in there?” doubt from the chat-save survives. Replace needs a second click.

§03 Variant B — two faces, real fingerprint

Same page as A, but the chip shows the key’s real edges — first five and last four characters, dots between. That answers the exact doubt from 2026-09-12: “I saved a key in the chat, but it is not here.” Needs one backend line: settings expose a tavily_api_key_hint alongside the existing tavily_api_key_set; the full key still never leaves the backend (the model tab’s eye-toggle comment states that rule).

Gains

The reader can match the fingerprint against the key in their password manager — the only variant that proves “my key made it”, wherever it was saved (chat card, this tab, or long ago).

Costs

A backend change and a new settings field. Nine visible characters of a secret — Tavily keys are low-blast-radius, but it is a precedent the provider keys would inherit questions about.

§04 Variant C — exactly the Model tab's pattern

Minimum novelty: the stored state, too, is exactly the Model tab’s — the input stays visible as the replace affordance (placeholder saying so), Remove sits beside it as a red button, and the guide block is gone. Nothing on this tab exists that a provider-key step does not have.

Kept in the stored state (user decision 2026-09-12): the allowance line. It is a plan fact, not a pitch — the reader budgets their searches against it. Reworded for this state: “no credit card” matters only before signing up, so it stays in the empty state’s guide block and leaves here.

Gains

One pattern for every key in the app — a reader who has set up a provider key already knows this page. Replace needs no extra click. Smallest diff in the component.

Costs

The stored state keeps an empty input as its largest element — the “key is not here” misreading survives, softened only by the placeholder. The sell moves but does not shrink.
